# 上下文瘦身：可复用的跑法

2026-11-11 第一次跑（AGENTS 4411→2584 字符，GLOBAL 1795→1702，skill 描述 4600→约 2200，删 3 个低频 skill）。
**模型升级、或觉得"最近变笨了/答非所问"时，照这个顺序再跑一遍。**

## 0. 先量，别先改

分两类列出来，各自多少字符：

| 类 | 都有什么 |
|---|---|
| **每轮加载**（真正花钱的） | GLOBAL.md、自动注入的 daily 日志、所有 skill 的 `description`、系统提示 |
| **按需加载** | 根 AGENTS.md、SKILL.md 正文、references/*.md |

经验值：真正贵的是「日志注入 + skill 描述」，不是 AGENTS.md。先动最大的那块。

## 1. 每段只做一个动作

`修` / `删` / `挪` / `改写` / `保留`，每条附一句原因。**改之前先把清单发给人确认。**

## 2. 判断能不能删的三问

1. 删掉之后我的行为会变吗？（"先读再改""跑测试""注意边界"——本来就会做，删）
2. 一个步骤删掉后还能换条路达到同样结果吗？（能 → 删；只有顺序本身是约束才留：先验证再发布、先确认再删除）
3. 同一件事说了三遍吗？（换成一个词，见 §4）

## 3. 判断"位置不对"而不是"写太多"

- 只在某个场景用的细节 → 搬进 `references/`，根文件留一行"什么时候去读"
- 同样输入永远同样输出 → 写成脚本（例：开工对表 → `tools/preflight.py`）
- "做 Y 之前先读 X" → 改成做 Y 时由失败信息/脚本把 X 顶出来
- 跨项目硬约束才进 GLOBAL；项目里的进 AGENTS；项目某类活儿的进 SKILL

## 4. 词汇化

反复出现的三句话 → 一个词，然后在 GLOBAL 写一次定义。
现在这套：**green / clean / tight / idempotent / 报告腔**（定义在 GLOBAL.md「用词」）。
口号类要求 → 换成能对照的行为描述 + 一组 NO / OK 例子（例：报告腔）。

## 5. skill 描述只写三件事

`做什么` · `什么时候用（触发词）` · `不用于什么`。
排序规则、输出格式、注意事项一律挪正文或 `references/`。

## 6. 绝对不能删的

- 偏好、被否掉的方案及原因、机器环境
- 不报错的坑、"看着像出错其实正常"的现象
- 「从不写入」「不上传」这类半句约束
- 删数据 / 花钱 / 发布 / 提权 / 改写已推送历史 —— 不可逆操作的规则（原样整段搬，别改写）
- 带日期的拍板决策

## 7. 搬的规矩

**先搬到正确位置，再压缩。能整行搬就整行搬，不要边搬边改写。**
根目录**不要**建 `CLAUDE.md`（会让 Claude Code 不读 `AGENTS.md`）。

## 8. 验收（缺一不可）

1. `paths:` 里的 glob 都匹配到真实文件（本仓库暂无 `.claude/rules`，此步跳过但每次要确认一次）
2. grep 一遍被拆走的旧文件名，不能有残引用
3. **列出所有消失的行**，逐行对清单
4. 交给一个**没参与精简的 agent**：只给它消失的行 + 仓库，让它搜关键词，不给你的结论；找不到的原样恢复
5. 暗号测试：在新文件里埋 `<!-- seal: XXXX -->`，开新会话读一个匹配文件问暗号，再读不匹配的做反向对照
6. `python3 tools/build.py` 必须 green（`check_skills.py` 会拦：脚本未登记、SKILL 超 100 行、skill 未同步）

## 9. 已知的坑

- `check_skills.py` 要求每个 `tools/*.py` 都在文档里出现 → 删脚本说明时别把名字一起删
- SKILL.md 上限 100 行，压超了构建直接失败
- repo `skills/` 是单一源，build 时同步到 `/var/minis/skills`；直接改后者会被覆盖
- 判断"skill 有没有人用"不能 grep 名字：系统提示里每轮都有全部 skill 名，计数会被污染；`atime` 在挂载盘上等于 mtime。要证据只能扫会话的 `tool_calls`（`minis-sessions-cli messages --id … --tools`），成本高，建议只对候选扫
