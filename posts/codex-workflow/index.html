这组资料的共同结论是：AI 编程的上限不在“让模型多写几行代码”，而在 上下文、计划、验证、审查和人的判断 能不能跟上。

核心判断

Codex 更像一组能力很强、但需要明确上下文的新同事，而不是一个可以无条件接管工程责任的按钮。

适合交给 Codex 的部分：

  • 阅读大代码库，梳理调用链、数据流和模块关系。
  • 在明确架构和示例下补功能、写样板、做跨平台迁移。
  • 根据测试、CI、日志、截图反馈迭代修复。
  • 并行探索多个方案，生成草案、报告、测试和 review 意见。

必须由人把关的部分：

  • 产品体验和真实用户路径。
  • 架构边界、依赖方向、长期可维护性。
  • 哪些场景必须正确，哪些只是局部能跑。
  • 最终合并、发布、责任和风险判断。

一套可复用流程

阶段 人做什么 Codex 做什么
定义边界 写目标、约束、验收标准、不能破坏的规则 读取相关文件，复述它对系统的理解
规划 纠正理解偏差，确认改哪些文件、引入哪些状态和逻辑 产出小型设计文档或实施计划
实施 分批派发任务，控制范围 按计划改代码、补测试、跑验证
审查 看 diff、跑关键路径、判断取舍是否合理 解释改动、定位失败、提出修复
沉淀 把有效流程写进 AGENTS.md、项目文档或知识库 下次复用同一套规则

这和 [[Resources/LLM Wiki 实践指南|LLM Wiki 实践指南]] 是同一个逻辑：先编译上下文，再复用上下文。

官方最佳实践六支柱

OpenAI Codex Best Practices 的落地思路可以压缩成六个支柱：

  • 从正确的任务上下文出发。
  • 用 AGENTS.md 写入持久指引。
  • 用配置文件统一跨会话行为。
  • 用 MCP 连接外部系统和工具。
  • 把重复工作封装成 Skills。
  • 把稳定流程变成 Automations。

这说明 Codex 的使用重点不是“每次写一个更长的 prompt”，而是把上下文、规则、工具、复用流程和验证方式逐步系统化。

Prompt 四要素

复杂任务的 prompt 至少要说清四件事：

要素 要回答的问题
Goal 这次到底要改什么、完成什么。
Context 相关文件、目录、文档、报错、截图和历史决策在哪里。
Constraints 哪些 API、数据格式、依赖、架构边界和安全规则不能破坏。
Done when 什么证据证明任务完成：测试、lint、截图、复现路径、diff 范围或剩余风险。

其中 Done when 很关键。没有完成标准，Codex 容易把“代码写完了”当成“任务完成了”；有完成标准，Codex 才能围绕验证器循环。

复杂任务先计划

复杂任务不要直接让 Codex 开写。更稳的三种方式：

  • 用 Plan mode，让它先读代码、解释当前结构、列方案和风险。
  • 让 Codex 反过来提问，先挑战需求假设，再变成可执行任务。
  • 在仓库里维护 PLANS.md 或计划模板，让长期任务有固定执行格式。

典型做法是两步走：

第一步：只读代码，不改文件，解释当前流程和最小改动方案。
第二步：人工确认方向后，再按方案实现、测试、review。

这比直接让 Codex “重构某某系统”慢几分钟，但能减少大面积跑偏。

AGENTS.md 的价值

Sora Android 团队的经验是：Codex 不能自动知道团队偏好的架构模式、静态检查、产品规范和真实用户行为，所以要把这些规则写进 AGENTS.md。

适合写入规则的内容：

  • 项目结构和模块边界。
  • 必跑的格式化、静态检查、测试命令。
  • 常见错误和禁止事项。
  • 代表性功能或参考实现。
  • 本地仓库、文档、知识库位置。

对这个 Vault 来说，AGENTS.md / CLAUDE.md 的作用就是让后续 agent 知道：剪藏要先编译进 Wiki，处理完原文再移到 Sources/Inbox/。

AGENTS.md 要短而准确。它不是百科全书，而是工程协议：目录结构、验证命令、约束边界、常见错误和 PR 要求。重复踩坑两次以上，就把纠正规则写进去；如果内容变长，把具体 review 规范、架构说明、发版流程拆成独立文档再引用。

配置、Skills 与 Automations

一次性 prompt 适合探索，稳定流程应该沉淀：

  • ~/.codex/config.toml 放个人默认值，如模型、推理强度、sandbox、approval、MCP、profile。
  • 仓库配置放团队共享偏好，避免每个会话重新解释。
  • Skills 用来封装可复用方法，比如日志分析、PR review、发版说明、迁移方案、故障摘要。
  • Automations 用来定义节奏，比如每日摘要、定时检查 CI、扫描可能 bug、生成发版说明。

Skills 定义方法，Automations 定义节奏。还没稳定的流程先不要自动化，否则只是把不可靠行为规模化。

Session 管理

Codex session 不是普通聊天记录，而是带上下文、决策和操作历史的工作线程。

实用原则：

  • 每个任务一个线程，而不是每个项目一个线程。
  • 同一问题还在延续时留在原线程，真正分叉时再 /fork。
  • 长线程及时 /compact，避免上下文膨胀。
  • 并行 agent 要配 worktree 或清晰写入边界，避免多个线程改同一批文件。
  • 让 Codex 像后台任务一样跑完，再 review diff；不要像盯初级员工一样盯每一步。

智能体优先工程

OpenAI 的 agent-first 工程经验可以拆成几个原则：

  • AGENTS.md 是地图，不是百科全书。它应该指向关键文件、约束和验证方式，而不是把所有细节塞进去。
  • 仓库本身是记录系统。产品规格、执行计划、质量标准、安全要求和决策记录都应版本化，方便人和 agent 共同读取。
  • 应用要变得 agent-readable。日志、metrics、traces、错误信息、测试输出和浏览器调试入口，都会直接影响 agent 能否自我修复。
  • 约束要尽量机械化。能用 lint、结构测试、类型检查和 CI 固化的规则，不要只靠口头提醒。
  • 要做 AI residue garbage collection。agent 生成的重复代码、临时方案、过时文档和半成品，需要定期清理。

这意味着工程师的角色不是消失，而是从“每行代码的作者”转向“系统边界、环境、反馈回路和杠杆的设计者”。

Claude Code 高强度使用经验

高强度使用 Claude Code 的经验和 Codex 基本同构：

  • 现有项目优先用 Plan Mode，让 agent 先读代码、列计划、解释风险，再开始改。
  • 低风险原型可以更快推进，但正式项目要小步迭代，不要一次性丢超大任务。
  • 上下文管理很关键：计划写进文档，长会话及时 /compact，复杂任务拆给 subagent 或新会话。
  • 重复提示可以做成 commands；工具链可以接 MCP、LSP、文档和项目管理系统。
  • 每个小功能后都要编译、测试、lint 或跑关键验收路径。
  • 不要让工具把自己逼死。AI 加速以后，人仍然要管理节奏、注意力和判断疲劳。

这部分经验可以直接写进项目的本地 agent 规则，让后续会话复用。

AI 专家委员会与 Worktree

“如何让 AI 写好代码”的案例补充了一个很实用的分工模式：不要假设一个 agent 永远最强，而是把不同工具放在不同岗位上。

可复用分工：

  • Claude Code：架构、UI 设计、交互打磨和主力开发；
  • Gemini CLI：大上下文扫描、文档、测试和重构建议；
  • Codex：复杂 bug 定位和另一条推理路径；
  • CodeRabbit：PR 自动 review，再让主力 agent 判断哪些意见值得修。

这个模式要配合 Git Worktree 或独立分支使用。每个 agent 在独立工作区里探索，最后通过 PR、diff 或人工 review 回收结果，避免多个 agent 在同一工作区里互相污染。

这和 [[Resources/Agent Infra 与 Runtime|Agent Infra 与 Runtime]] 的判断一致：agent 能力变强以后，环境隔离、分支、调度和回收机制会变得更重要。

对抗 AI 代码熵增

AI 产出代码很快，技术债累积也会很快。有效做法不是少用 AI，而是给 AI 更清楚的工程边界。

需要长期维护的几件事：

  • AGENTS.md、CLAUDE.md、GEMINI.md 这类规则文件保持同步；
  • 发现文件过长、重复逻辑或复杂度上升时，及时要求拆分和重构；
  • 每次重构同步更新测试和文档；
  • 用 review agent 找边界问题，再由主力 agent 和人一起判断；
  • 不把“100% AI 写代码”误解成“人不需要负责架构和质量”。

苏格拉底式编程

高质量 AI 编程不是只写命令，而是持续追问。

有价值的问题包括：

  • What is your opinion?
  • Do you have a better idea?
  • 这个 UI 有没有更优雅的交互？
  • 这个概念需要单独存在吗，还是应该和已有对象合并？
  • 如果保留用户体验的一致性，技术实现应该如何分层？

这种问法的价值在于：让 AI 不只是执行用户已经想到的方案，而是参与发现更好的产品和技术表达。人的责任从逐行编码转向品味、边界和问题定义。

并行 agent 的真实瓶颈

多开 Codex 会话不等于线性提速。并行会话越多，人类的工作越像技术负责人：

  • 要分配任务，避免多个会话改同一块逻辑。
  • 要审核每个会话的计划和 diff。
  • 要整合结果，处理冲突和重复实现。
  • 要判断哪些探索可以丢弃。

因此，AI 提效后的瓶颈常常从“写代码”转移到“决策、反馈和整合”。

不要只用 AI 做旧事

[[Resources/AI 商品化与价值迁移|AI 商品化与价值迁移]] 提醒：如果只是用 AI 更快生成传统形态的软件，可能只是“用电动机驱动旧工厂”。真正的效率提升，通常来自围绕新能力重新设计流程。

对工程工作流来说，就是：

  • 不只让 AI 写代码，还要让它参与读代码、建计划、跑验证、生成审查材料。
  • 不只看生成速度，还要看 review、集成、测试是否变成新瓶颈。
  • 不只追求多 agent 并行，还要设计任务边界和整合机制。
  • 不只沉迷一次性原型，还要把有效模式写进 AGENTS.md、文档和知识库。

验证器比野心重要

长时间运行任务、Goals、自动化和 dynamic workflows 都需要可验证终点。没有验证机制的目标，只是在许愿。

好的验证器包括：

  • 单元测试、集成测试、端到端测试。
  • 可以稳定复现的 bug。
  • 性能基准或对比矩阵。
  • 截图、浏览器检查、交互验收路径。
  • 日志、监控、回归清单。

当任务很长时，先让 Codex 把计划保存成文件；跨会话继续时，新的实例先读计划，再执行下一步。

反面提醒

[[Sources/Inbox/Why I Don’t Vibe Code|Why I Don’t Vibe Code]] 的价值在于提醒：AI 能降低 accidental complexity，但不能消除 essential complexity。

需要保留的摩擦：

  • 深读代码时形成的真实理解。
  • 写 ADR 时暴露的取舍和假设。
  • 团队 review、用户研究、测试、合规这些看似慢的环节。
  • 对数据来源、抽象模型和系统边界的怀疑。

如果工程师自己不知道好坏，只让 AI 一路“写穿摩擦”，结果往往是能跑但难维护的复杂度。

官方最佳实践也点名了几类常见错误：

  • 把持久规则塞进每次 prompt，而不是写进 AGENTS.md 或 Skill。
  • 不告诉 Codex 构建、测试和验收方式。
  • 复杂任务跳过规划。
  • 还没理解工作流就给完整权限。
  • 多线程并行但不用 worktree 隔离。
  • 工作流还没手动验证可靠就自动化。
  • 每个项目只开一个超长线程。

对个人求职的用法

这组资料可以转成面试表达：

我会把 Codex 当成很强的新同事来用，而不是直接替我做工程判断。实质性改动前，我会先让它读代码、复述数据流和模块边界，再一起制定计划。实施时可以让它补代码、补测试、跑验证，但架构取舍、用户体验、异常边界和最终 review 还是我负责。AI 提高的是产能，不是免除工程责任。
