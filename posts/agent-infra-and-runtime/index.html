Agent Infra 与 Runtime

June 8, 2026 · 原创
来源当我们在谈论 Agent Infra 时我们在谈论什么

这篇文章的核心观点是：Agent Infra 不是训练基础设施，也不是推理服务本身，而是更靠近应用层的 Agent Runtime。它要解决的是 agent 执行复杂任务时的环境、协作、调度、状态和失败恢复问题。

一句话结论

真正决定 agent 能不能承担复杂任务的，不只是模型聪不聪明，而是执行是否可控、失败是否廉价、环境是否可替换、协作是否有基础设施兜底。

典型 Agent 架构

一个常见 agent 系统通常包含：

组件 职责
LLM / Reasoning Core 理解上下文、生成计划、决定下一步行动
Planner / Executor 拆解复杂目标并逐步执行
Tools / Skills 封装 API、代码执行、数据库、浏览器等外部能力
Memory / Context Store 保存中间状态、历史行为和长期偏好
Env action 依赖的真实或虚拟执行环境

这些组件被 agentic loop 串起来：观察状态、思考、行动、获得反馈，再继续下一步。

当前瓶颈

顺序执行限制复杂任务

多数 agent 仍然是一步一步执行：做一步、等反馈、再做下一步。复杂任务往往需要多路径探索和并行试错，单线程 loop 很容易被某一步失败卡住。

Agent 协作还停留在协议层

A2A、MCP、多 agent 框架解决了一部分“能不能通信”的问题，但还没有充分解决“怎么稳定协同”的问题。真正的协作需要任务分支、共享上下文、消息总线、生命周期管理和失败恢复。

长程任务会污染环境

复杂任务里的 action 大多有副作用。执行越久，工作区越容易混乱：临时代码、重复文档、日志风格不一、多个 subagent 覆盖彼此修改。

Git Worktree 是当前 coding agent 场景里最朴素也最有效的隔离方案：每个 agent 在独立工作区里探索，最后只回收 diff 或 PR。

物理世界最后一公里很脆弱

没有稳定 API 的现实任务，比如下单、支付、预订、登录、风控验证，很难只靠 tool 调用解决。现实世界有大量隐式状态，agent 需要更可控的执行环境和可复现的 action。

Skill + Env = Box

文章提出一个很有启发的抽象：Box = Skill + Env。

Box 不是单纯的工具函数，而是把某个能力和一个可复现、可丢弃的执行环境绑定在一起：

  • action 在隔离环境里执行；
  • 成功路径可以缓存和复用；
  • 失败路径可以直接丢弃；
  • 对上层暴露语义化接口，而不是暴露底层执行细节；
  • 多个 box 可以组合成更复杂的能力。

这个思路和容器、不可变基础设施、IaC 的历史经验很像：不要只要求人小心，而是让系统提供稳定、可重复、可销毁的执行基础。

Agents 的 Kubernetes

如果每个 action 都能放进 box，那么下一层需求就是调度和管理这些 box。

可能的 Agent Runtime 组件：

组件 作用
Context Manager 管理结构化上下文、对话历史、文件空间和协作状态
Branching 把任务执行中的不同可能性变成一等能力，多路径探索但不共享副作用
Messaging Hub 让 box / agent 之间发送消息、订阅事件、汇报进展
Scheduler + Lifecycle Manager 控制并发、超时、取消、重试、失败恢复和资源分配
Box Runtime 提供可复现、可丢弃、语义化的执行环境

对 coding agent 来说，这相当于把现在手工使用的 worktree、分支、PR、日志、测试和临时工作区，升级成可编排的基础设施。

对个人和项目的启发

可以直接迁移到自己的工作流：

  • 复杂任务不要让多个 agent 共享同一个脏工作区。
  • 每个探索方向用独立分支、worktree 或明确的文件边界隔离。
  • 让 agent 输出 diff、报告和验证结果，而不是直接把所有尝试混进主线。
  • 对长任务保留上下文文件、执行日志和停止条件。
  • 把可复用能力沉淀成 skill、脚本、命令或规则文档。
