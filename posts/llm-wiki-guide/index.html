LLM Wiki 实践指南

这篇是从 LLM Wiki 和 Obsidian + Claude Code：用 Karpathy 的方法，搭建真正可用的第二大脑 编译出来的操作指南。

核心不是“把文章存起来以后再搜”，而是让 agent 先完整阅读资料，再把知识编译进一个持续维护的 wiki。

核心区别

模式 工作方式 问题
普通收藏 把文章、截图、文档丢进文件夹 资料越来越多，但没有结构，后面很难找回
RAG/临时检索 提问时再从原文片段里拼答案 每次都重新理解，长期积累弱，容易漏上下文
LLM Wiki 导入时就总结、归类、互链、更新索引 前期需要维护规则，但知识会持续复利

LLM Wiki 的重点是：知识只需要“编译”一次，之后通过 Index.md、专题页、实体页和交叉链接持续复用。

三层结构

层 当前目录 责任
Raw sources Sources/ 保存原始资料，作为 source of truth
Wiki Career/、Work/、Resources/ 保存整理后的知识、方法、项目复盘、沟通素材
Schema AGENTS.md、CLAUDE.md 约束 agent 怎么读、怎么写、怎么更新

这个 Vault 不再用 Notion/、interview/ 作为长期顶层名，因为它们更像来源或局部场景。现在顶层按用途命名：Career/、Work/、Resources/、Sources/、Attachments/。

导入时 agent 要做什么

导入一篇新资料时，不是简单移动文件，而是做一次小型编译：

  1. 判断资料类型：职业发展、工作项目、通用方法、剪藏阅读、附件。
  2. 保留原文到 Sources/：文章剪藏先进入 Sources/Clippings/ 待处理，处理完成后 raw 文件移到 Sources/Inbox/ 归档。
  3. 提取长期有价值的内容：概念、方法、事实、决策、风险、可复用话术。
  4. 更新已有页面，而不是重复造一堆孤立页面。
  5. 如果出现新概念，创建独立页面或专题页。
  6. 建立 Obsidian 双链，让原文、专题、实体之间能互相跳转。
  7. 更新 Index.md，让以后从索引就能找到它。
  8. 更新 Log.md，记录这次导入做了什么。

查询时 agent 要做什么

查询不是直接全库乱搜，而是按顺序来：

  1. 先读 Index，判断相关入口。
  2. 再读对应专题页，例如 Career/、Work/公司A/、Work/公司B/。
  3. 必要时回看 Sources/ 原文。
  4. 生成答案时带上 Obsidian 链接。
  5. 如果答案形成了可复用结论，写回 wiki，并更新 Index.md 和 Log.md。

定期修复检查

随着资料变多，知识库会出现几类问题：

  • 链接失效：文件移动后旧路径没改。
  • 页面孤立：有价值的页面没有被索引或其它页面链接。
  • 概念重复：同一个主题散在多个地方，没有主入口。
  • 结论冲突：新资料推翻旧判断，但旧页面还没更新。
  • 信息过时：需求、面试策略、项目状态已经变化。

巡检时 agent 应先生成问题清单，再根据用户确认修复。不要一上来就大规模合并或删除。

自我迭代闭环

每次新资料处理后，至少要满足这几个条件：

检查点 说明
原文可追溯 原始资料仍在 Sources/
知识已沉淀 有对应的 wiki 页面或已有页面被更新
索引可发现 Index.md 能找到新增或更新内容
日志可回溯 Log.md 有本次动作记录
链接可跳转 旧路径、图片路径、显式双链已检查

如果这五点都满足，才算一次完整导入。

常用指令

处理 Sources/Clippings 里的剪藏，按知识库规则编译，处理完 raw 文件移到 Sources/Inbox，并更新相关专题、Index.md 和 Log.md。

处理 Sources/Inbox 里的新资料，先判断是否已经是已处理剪藏归档；未处理的按知识库规则编译，更新相关专题、Index.md 和 Log.md。

基于 Index.md 和 Career/，帮我梳理职业准备还有哪些短板。

基于 Work/公司A/需求 和 Work/公司A/记录，整理公司A项目的业务地图。

lint 一下知识库，检查旧路径、断链、孤立页面、重复概念和过时内容。

使用外部 AI 时

如果要把这个知识库给另一个 AI 看，优先给它：

  1. Index.md
  2. AGENTS.md 或 CLAUDE.md
  3. 相关专题页面

Index.md 是目录和摘要，外部 AI 读它就能知道有哪些页面，再根据问题读具体材料，减少胡乱猜测。
