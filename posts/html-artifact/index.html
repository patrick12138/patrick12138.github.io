这篇文章的重点是：当 agent 输出越来越复杂时，Markdown 不一定是最适合人类审阅的最终形态。对于规格、报告、设计探索、代码 review 和交互式调参，HTML Artifact 往往更清楚、更可读、更容易分享。

什么时候用 HTML

场景 HTML 的优势
规格和规划 可以放 mockup、数据流、代码片段、选项对比和导航
代码 review 可以渲染 diff、严重级别、调用图、模块关系和批注
设计原型 可以直接做交互、动画、状态切换和参数面板
报告研究 可以把多源信息整理成图表、时间线、流程图
临时编辑器 可以做拖拽、筛选、表单、复制 JSON / Markdown / prompt

Markdown 仍适合长期知识沉淀和可编辑笔记；HTML 更适合需要视觉结构、交互、密集信息和一次性审阅的输出。

和 Codex 工作流的关系

[[Resources/Codex 与 AI 编程工作流|Codex 与 AI 编程工作流]] 强调“人要留在审查回路里”。HTML Artifact 的意义就在这里：它把复杂输出变成更容易被人审阅和操控的界面。

典型链路：

  1. 让 agent 读代码、资料或设计约束。
  2. 生成一个 HTML explainer / plan / review 页面。
  3. 人在页面里比较方案、查看批注、调参数。
  4. 页面导出 prompt、JSON、diff 或 Markdown。
  5. 再把结果交给 agent 执行或写回文档。

可复用 prompt

把这个问题整理成一个单页 HTML artifact：
- 顶部给 3 句话结论；
- 中间用表格比较方案；
- 用流程图说明数据流；
- 标出风险点和待确认问题；
- 最后提供可复制的实施计划。

帮我 review 这个 PR，生成一个 HTML artifact：
- 渲染关键 diff；
- 按严重级别标注问题；
- 解释核心调用链；
- 给出需要人工确认的点；
- 最后生成一份可复制的 review comment。

为这个配置/提示词/任务列表做一个一次性 HTML 编辑器：
- 左侧可编辑；
- 右侧实时预览；
- 显示约束、依赖和警告；
- 提供 copy as JSON / Markdown / prompt 按钮。

Claude Artifacts 完整能力（2026 更新）

来源：[[Sources/Inbox/What are artifacts and how do I use them|What are artifacts and how do I use them]]（Anthropic 官方文档, 2026-03）

Claude Artifacts 已从单纯的"独立内容展示"进化为一套完整的应用生成和分发平台。以下补充本页未覆盖的新能力。

AI-Powered Artifacts

Artifacts 可以内嵌 AI 能力，变成 AI 驱动的应用。用户通过文本 API 使用 Claude 的智能——问答、创意生成、个性化教练、游戏、问题解决。

  • 创建者只需描述想要什么 → Claude 写代码 → 应用运行在 Anthropic 基础设施上
  • 使用者用自己 Claude 账户认证，消耗自己配额，不给创建者增加成本
  • 分享免费，无论 10 人还是 10000 人

MCP 集成

Artifacts 可通过 MCP（Model Context Protocol）连接外部服务（Asana、Google Calendar、Slack 等），也支持自定义 MCP 服务器。首次交互需用户批准，偏好持久化。

持久化存储

Pro/Max/Team/Enterprise 计划支持跨会话存储：
- 个人存储：每个用户独立数据（如日志只自己可见）
- 共享存储：所有用户看同一份数据（如排行榜）
- 20MB/artifact 限制，纯文本
- 取消发布会永久删除存储数据

版本控制与多 Artifact

  • 使用版本选择器在前端切换版本
  • 编辑历史消息可产生不同对话分支，各有独立 artifact 集
  • 可同时打开多个 artifact，通过 chat controls 切换

错误处理

artifact 出现错误时，点击 "Try fixing with Claude" 自动把错误信息复制到新消息，让 Claude 诊断修复。

与本页原有内容的关系

本页原有的 HTML Artifact 使用场景（方案对比、代码 review、设计原型等）仍然成立。新增的 AI-powered、MCP 集成和持久化存储能力让 Artifact 从"一次性展示"升级为"有状态应用"——可以用来做日志、追踪器、仪表盘、协作工具等需要状态保持的东西。

本 Vault 的长期知识仍优先用 Markdown，因为 Obsidian 双链、索引和长期维护更适合 .md。

HTML 更适合临时或半持久产物：

  • 复杂方案对比；
  • 项目复盘可视化；
  • UI / 数据流审查；
  • 面试话术演练器；
  • 需要交互调参的提示词或配置。

如果 HTML 里的结论有长期价值，应再编译回 Markdown wiki 页，并更新 [[Index|Index]] 和 [[Log|Log]]。
